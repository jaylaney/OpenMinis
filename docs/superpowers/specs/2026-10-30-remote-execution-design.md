## Intent and accepted direction

Extend OpenMinis with a custom iOS build and a native macOS companion. When creating a chat on the iPhone, choose this phone or a saved Mac as the execution environment. A Mac chat runs OpenMinis' own agent on the Mac; the phone displays and controls it.

The user selected OpenMinis' own agent, an OpenMinis extension, away-from-home access through Tailscale, and terminal/file access initially. The revised direction uses the separately installed Tailscale apps on both devices and a manually entered Mac Tailscale address. Automatic iCloud discovery is deferred. Keep one-time application authorization: a network address is not an execution credential.

Goals: visibly bind each chat to one execution host; run the full agent loop and tools there; stream progress and approvals; stop work; reconnect without duplicating it; preserve existing local iPhone behavior.

Initial exclusions: embedded tsnet; our own relay; automatic host discovery; remote control of the phone; desktop/screen/browser automation; interactive PTY; unattended startup; waking a sleeping Mac; live session migration; offline execution queues; automatic rerun after crashes; rolling a host back through snapshots or virtual machine reverts; existing-agent adapters; other operating systems.

The following are author-proposed delivery defaults, not additional user decisions: one enrolled phone/controller per Mac; multiple locally saved Macs; one active run per Mac with no prompt queue; one existing API-key provider for the first real-agent milestone; per-action approval by default with an explicitly enabled run-scoped mode; a local user-presence check (biometric or passcode) before enabling that mode, with none required per approval. These keep the first slice bounded and are reviewable before implementation planning.

## Approaches and selection

| Approach | Tradeoff | Decision |
| --- | --- | --- |
| Shared OpenMinis agent and platform runtimes | Refactor existing orchestration, while keeping one agent implementation. | Selected. |
| Mobile frontend for existing Mac agents | Requires adapters and differing session/approval semantics. | Not selected. |
| Standalone new product | Adds independent product and infrastructure work. | Not selected. |
| External Tailscale plus saved endpoint | Manual network setup; ordinary native sockets; no new embedded-node integration. | Selected for v1. |
| Embedded tsnet plus iCloud registry | Automatic discovery and in-app networking, but new iOS UI/lifecycle/FFI and Mac packaging. | Deferred; not assumed cheaper because Go source exists. |
| Application relay or CloudKit command mailbox | Adds server operation or delayed command-delivery/replay semantics. | Excluded. |

Use a native Swift macOS companion with native process/file adapters. Mac Catalyst is an alternative worth a bounded dependency/spawn feasibility assessment if planning uncovers a compelling saving; it is not assumed to support the desired execution model. Running the existing Designed-for-iPad app on Mac does not establish native host capability. Do not replace the selected architecture with Catalyst without reporting the evidence and scope change.

## Components and incremental extraction

The phone gets a local-session backend and a remote-session backend. Remote sessions never instantiate a local executing loop. The Mac owns model calls, tools, admitted history, approvals, and persistence. The phone owns drafts, view preferences, and a non-authoritative cache.

Extract shared orchestration behind explicit provider, storage, tool-runtime, event, and approval interfaces. UIKit, speech, permission presentation, iSH, and platform lifecycle remain in adapters. Make each extraction behavior-preserving on iOS; add characterization coverage before moving behavior. A synthetic transport stub is allowed for qualification, but is not a second production agent loop.

First prove the native connection and durable run protocol independently. Then extract the smallest vertical slice supporting the selected API-key adapter, text conversation, same-provider request retry, native shell/files, and user questions. Compaction follows as its own step before combined qualification; title generation is deferred. Do not require the entire current agent surface to be portable before testing anything on Mac. Future retry, compaction, cancellation, and history changes should update one shared implementation and exercise both adapters; platform exceptions must be explicit capabilities.

The Mac app provides hosting controls, pairing/revocation, provider/workspace setup, active-run status, local approvals/Stop, and diagnostic status. It is initially a host/settings app rather than a full desktop chat interface. Closing a settings window leaves hosting active; explicit Quit shuts it down.

## External Tailscale and connectivity

Both devices use the separately installed Tailscale clients. The app does not manage login, node keys, expiry, routing, or embedded-node state. The user enables Tailscale and permits the service through tailnet policy. The phone saves a Mac tailnet IP and service port; a name can be supported later without changing host identity.

Use ordinary native TCP/TLS networking over the system route. Bind the Mac listener to its selected Tailscale address, not every LAN interface. If that address disappears, stop listening and report unavailable; re-bind when it returns, since this happens whenever the VPN toggles. Do not expose Funnel, public forwarding, or silently try LAN/public addresses. No Swift/Go byte-stream bridge, app-managed tsnet listener, or new Go networking archive is required.

Distinguish transport timeout/unreachable, TLS identity mismatch, unapproved controller, incompatible protocol, and host busy. Without privileged Tailscale diagnostics the app may not know whether a timeout means VPN off, a different tailnet, policy denial, sleep, expiry, or outage; present these as troubleshooting possibilities rather than invented diagnoses. Re-login and expiry settings belong in Tailscale. A live authenticated capability check, not a saved last-seen time, makes Send available.

The Mac must be running and reachable. The phone may disconnect while accepted work continues. Tailscale's network encryption does not keep model requests local: the Mac sends permitted context to its selected model provider. Logging/privacy settings of the external Tailscale clients are separate from our application logs. Application logs default to operational IDs and states; redact enrollment secrets, credentials, authentication material, raw prompts, and full command/file contents. Inspect retained integration logging before claiming this privacy contract is satisfied.

## Enrollment, identity, and revocation

Use per-installation application identity keys, stored under new non-synchronizable Keychain service names/access groups appropriate to these signed builds. A stable opaque host ID is bound to its approved key; neither the existing UUID, display name, IP nor Tailscale membership grants application authority. Deriving the ID from the key is optional; silent key replacement is forbidden.

Manual enrollment:

1. Locally enable hosting and open a short pairing window on the Mac. Display its endpoint and a one-time invitation containing the full host-key fingerprint and a high-entropy enrollment secret. Offer it as both a QR code and copyable text, using system frameworks with no new dependency; the builder chooses the encoding. Pairing must not depend on Universal Clipboard, which needs a shared Apple account that remote execution does not otherwise require.
2. Scan the QR code, or enter the endpoint and invitation as text if the camera is unavailable or denied. The phone verifies the Mac TLS key against that fingerprint before transmitting enrollment data. Never globally accept an untrusted certificate or send chat data during tentative enrollment.
3. In the encrypted enrollment exchange, present the phone's identity key and invitation secret. Derive a short code from both keys and the invitation, and show it on both devices. The Mac's local confirmation displays the code and the user confirms only on a match, before the Mac stores that exact controller key; any device name in the request is untrusted display data. Consume the invitation once, including on rejection; close the pairing window. Expiry and rate limits are mandatory, with concrete values selected in planning.
4. Retain the Mac key pin on the phone and the controller allowlist on the Mac. Normal connections require mutual application authentication. A changed IP may be edited without changing the pin; a changed key requires new enrollment.

Outside pairing, reject unknown keys before exposing sessions/tools. Bound unauthenticated parsing and requests. Use standard TLS and platform trust APIs, with explicit pinned-peer validation. Pin the host's public key (SPKI), not its certificate, and ignore certificate dates in that validation, so expiry or reissue under the same key does not force re-enrollment. Authenticate the controller with an application-layer signature over a TLS exporter value as the chosen channel-binding mechanism, rather than requiring client certificates. Built-in Security certificate APIs mainly consume encoded certificates; Apple also publishes swift-certificates, which supports X.509 creation, so certificate generation is not an Apple-platform impossibility. The installed SDK exposes TLS exporter APIs; qualify their use on the actual native connection in gate 1. Process nothing but that exchange until it succeeds. Keys stored in Keychain may be used in memory for signing; this design does not require nonexportable hardware keys or a Go signer bridge.

One enrolled controller per host is the proposed v1 limit. Replacing it requires local Mac action. Local Mac approval and Stop always work without a connected phone. Revoking a controller first blocks new admissions and invalidates its grants/approvals, then closes connections and cancels its managed run. Store controller/run ownership explicitly even with this initial limit. Controller replacement/revocation, explicit per-run controller ownership, and schema version/migration planning remain pre-production host integration gates; the initial admission package implements none of those workflows. Deleting its database is not a phone replacement procedure.

An unlocked enrolled phone has control authority. Fresh human presence for every approval is not promised; adding it is a separate product/security choice. Enabling a run grant is the exception: it requires the local user-presence check described under the approval policy. Remote removal of a lost phone through Tailscale can cut future connectivity, but is not application revocation and does not stop an already admitted run. The Mac app remains the authoritative revocation/Stop path initially.

Protect secrets and allowlist integrity with Keychain and careful storage; scrub child-process environments. These measures do not isolate the host from arbitrary approved shell code running under the same OS user. Such code can compromise user-owned app files or persistence. Do not promise that Keychain, HMACs, or encryption alone prevent this. Strict same-user-shell isolation would require a separately selected OS boundary before making that guarantee.

## iCloud and credential boundaries

Automatic iCloud host registration and all hosted transcript/secret sync are deferred. The Mac does not start existing `SyncCore` or `CloudSyncEngine`, reuse `SyncDeviceV2`, or call existing synchronizable credential writers. Configure the initial API key locally on Mac using separate non-synchronizable storage. Existing local iPhone sync behavior remains unchanged.

The remote execution path itself does not require the same Apple account. Optional background attention notifications do: both builds must access the same developer-owned private CloudKit container/account and environment. No access to upstream OpenMinis containers is assumed.

Use only a separate `ExecutionAttentionV1` record/subscription path for that optional feature. Store opaque recipient/host/session identifiers, event kind/nonce, and time; no commands, file paths, prompts, secrets, or approval decisions. CloudKit/APNs may display a generic alert such as “A Mac task needs attention.” Opening it connects to the pinned host and fetches current state. A notification never authorizes an action, supplies an approval body, or becomes an execution mailbox.

Notifications are best effort and may coalesce. A missed/delayed/duplicate/stale hint must be harmless. On reopen, fetch all actual outstanding attention from the host. Without notification permission, iCloud access, or successful setup, show “background alerts unavailable”; the remote feature still works while open, and unattended runs may wait silently for the user to return. No automatic approval or retry compensates for missing alerts.

Custom-signing inventory includes fixed app-group and container identifiers, Keychain groups/service names, `CKContainer.default()` callers, HealthKit/HomeKit/NFC/WeatherKit capabilities, and extension targets. Keep the optional attention writer separate from ordinary sync even when sharing a container. Physical qualification must use matching CloudKit development/production environments with the schema deployed as appropriate. Disabling attention must not disable manual host access.

## Session authority, journal, and reconnect

A host session has an immutable execution host ID/key binding separate from legacy `remoteDeviceId` or sync-origin metadata. Existing local sessions retain existing behavior. No in-place host migration or legacy Fork Session path is offered for hosted chats.

Proposed v1 concurrency: one active run per Mac, no admitted prompt queue, and one controlling phone. A send while busy is explicitly rejected; its text remains a phone draft. A run waiting for a user decision holds the active slot only until that decision expires, so one ignored request cannot block the Mac indefinitely. The phone can save multiple Macs and each host can retain multiple idle sessions. This deliberately narrows existing iOS prompt-queue behavior without changing local iOS sessions.

Use one host-local durable authority for admission, canonical transcript, run/approval state, and events. Prefer admission/journal tables in the same SQLite transaction domain as host chat persistence. If a different storage design is chosen, the plan must specify recovery across its writes before it is accepted. Generic last-write-wins cloud records are never an authority for a running session.

Each mutating request has an authenticated storage epoch, stable request ID, session/run ID, and payload fingerprint. Use one ordered request channel per controller, and check invocation and run state inside the admission transaction, so a late approval after Stop is rejected. Persist admission before any side effect; repeated identical IDs return recorded status, while changed payloads are rejected. Persist terminal rejections of valid authenticated requests, including busy responses, as well as admissions: retrying an ID rejected as busy must not execute later when the host becomes idle. An explicit later Send uses a new ID. After a lost acknowledgment the phone only looks up that request ID; it never resends automatically. Reconnect replaces and fences the previous controller-channel lease before processing requests on its replacement. All admission and status reconciliation use the same serialized authority. Before reporting an unrecorded ID as absent, atomically persist a terminal rejection tombstone for that ID; any delayed original request must then be rejected. No pending old-channel admission may commit after that definitive absence. A new explicit Send uses a different ID and cannot revive the tombstoned one. If the host has a record, the phone shows that status or result. If it has none, the phone says the Mac has no record, that the request may never have arrived or the Mac may have been restored, and keeps the text as a draft; sending again is an explicit user action with a new ID. An approval whose request is unrecorded stays pending, and the host must show the action as still awaiting a decision before it can be approved again. Stop may retry automatically for the same exact epoch/session/run while its request has no definitive terminal refusal. Never resurrect a tombstoned Stop ID: after `rejectedAbsent` or another terminal refusal, check that the same target still needs Stop and issue a new Stop request ID. A changed epoch never silently retargets an old Stop. A `stopRequested` record acknowledges the request, not process termination. Unknown execution outcome is never interpreted as failure-to-start.

The portable admission core returns `SubmissionResult` from submission, with the durable `RequestRecord` and an `isReplay` flag. Only a newly inserted, non-replay `admitted` result signals a new Start admission; an existing admitted record never authorizes launch, including after reopen. This marker is not a durable process-launch authority. A new Start refused during recovery is durably `rejectedBusy` and stays refused after recovery; explicit later Send uses a new ID. The journal acquires a nonblocking exclusive OS lock on a stable directory lock file before SQLite opens, holds it through connection closure, and never unlinks it. Concurrent owners fail before mutation. Initialization validates the configured controller in its transaction before changing recovery state; failed initialization releases ownership. No-op recovery confirmation preserves the existing connection lease.

The journal directory is a dedicated state leaf below a host-provisioned stable trusted parent. The core creates a missing leaf with mode 0700 and inspects directory type, effective-user ownership, owner rwx mode bits, group/other permissions and extended ACLs before opening the lock or SQLite. Symbolic-link leaves, permissive modes and all extended allow grants (including inherited grants) are rejected; ACL inspection failures fail closed. Existing directories, parents, contents and ACLs are not silently repaired. Host provisioning must explicitly repair older permissive state directories without losing the journal or epoch. Ordinary filesystem privacy does not isolate against hostile same-user code or create a shell sandbox; native filesystem qualification remains a later gate. Owner rwx is a mode-bit check, not proof of effective ACL access: deny-only ACLs may still cause a fail-closed EACCES at storage open. Reject dot path components before resolving the trusted parent with POSIX realpath; retain and inspect the original leaf without following it. All storage opens use that prepared path. Lock and SQLite opens use O_NOFOLLOW and SQLITE_OPEN_NOFOLLOW. Before opening storage, existing lock/database and known SQLite -journal/-wal/-shm files must be regular, effective-user-owned and singly linked; check the opened lock descriptor too. Refuse unsafe artifacts without repair. These checks assume the documented stable parent and do not provide hostile same-user race isolation.

The admission SQLite connection uses DELETE rollback journaling, synchronous EXTRA (native level 3), and fullfsync ON. EXTRA requests the directory synchronization after unlinking the rollback journal; FULL alone does not, and fullfsync changes the synchronization method rather than adding sync points. Native configuration readback and ordinary committed close/reopen are automated evidence for this policy, not a reproduced power-loss test. Genuine native power-loss/filesystem qualification remains pending. See the [SQLite synchronous documentation](https://www.sqlite.org/pragma.html#pragma_synchronous).

Public storage failures carry a stable kind and captured SQLite/POSIX codes through `JournalStorageError`. A failed rollback preserves the original cause and rollback cause in the distinct public `JournalTransactionError`, with both localized diagnostics. Host adapters classify errors by these fields rather than message parsing. AdmissionError supplies stable short payload-free localized case descriptions. Actual SQL NULL stays nullable; a non-NULL column text conversion failure immediately captures and throws its SQLite error instead of being treated as absent controller binding or optional data. Explicit rollback failure permanently disables that owner: every actor API, including cached status and connect, returns the retained composite until destruction/reopen, even if native autocommit later appears restored. No uncommitted run state may escape through reads; the failure must not reset the epoch, release authority or become a normal admission refusal.

Trusted host reads use throwing `status()` (`try await coordinator.status()`) and epoch-qualified `runStatus(for:epoch:)`. Connection reads use `status(over:)` and `runStatus(for:epoch:over:)`; both validate the current controller lease. Bootstrap status deliberately requires no known epoch so a new lease can discover reset state. Every run lookup validates the expected epoch before reading a run, and `RunRecord` includes that verified epoch. There is no public bare-RunID lookup.

Host-internal completion settlement also carries the storage epoch captured when the run was admitted. Validate that epoch before reading or updating a run; a delayed old completion must not settle a new-epoch run that reuses the same RunID. Never substitute the current epoch for the captured one.

Retain admission/dedupe metadata for the session lifetime, independently of compacted event payloads. Deleted sessions keep tombstones or an equivalent rejection boundary so old requests cannot recreate them. Every database loss/reset requires a fresh unpredictable storage epoch, authenticated by the pinned host, or a genuinely new host identity. Re-enrollment alone is insufficient if the old host key survives. Reject requests from earlier epochs before admission, even if the session/request ID is unknown in the new database. The phone must not relabel old pending mutations with the new epoch; restoring service requires an explicit new-session action after acknowledging the reset.

A restored database would keep its old epoch, and a host cannot reliably detect that rollback, so host state is kept out of restores instead. Before exposing service, the host must mark its state folder as excluded from backup and verify that policy, and store the host identity key as this-device-only. Backup exclusion is a host integration duty, not behavior implemented by the admission package. A Time Machine restore then comes back with no database, which is the database loss already handled above: a fresh epoch, with existing sessions unavailable after the phone acknowledges the reset. A move to a new Mac comes back with no identity key, so it is a new host requiring new enrollment. The cost is that Mac chat history is not backed up; after a restore, the phone's cache keeps committed transcripts readable. Both behaviors are platform knowledge until qualified on signed builds.

Rolling a host back through a snapshot or virtual machine revert remains unsupported in v1, because it brings back the excluded folder too. The Mac app provides a Reset Host action that creates a new host identity, after which existing sessions are unavailable and the phone must enroll again; the documentation tells users to run it after such a rollback. If a user skips it, two backstops remain: a phone cursor ahead of the host's head is treated as a reset, and because the phone never resends automatically, a rollback cannot silently rerun a request.

The host assigns monotonic event cursors per host within its storage epoch, covering session-list changes as well as session events. Only committed events carry durable cursors. Streamed deltas reference their last committed cursor plus an ephemeral sequence number, and never advance the phone's stored cursor. Reconnect asks for changes after the last committed cursor, or a consistent snapshot plus new cursor when deltas have expired. Because phone cursors are committed-only, a client cursor ahead of the host's committed head can only mean rollback, so the host treats it as a reset under the epoch rules above and never answers with an empty change list. Coalesce token output for persistence; clients may see uncommitted partial text disappear after a crash. Retain committed partials with an interrupted label. Never automatically replay a model request or tool after host restart; a new user turn intentionally repeating work can incur a new provider charge and repeat external effects. Dedicated rerun/edit-history controls remain deferred as specified below.

On every host startup, reconcile previous managed process groups before exposing any Start, and keep admission blocked outside the core until absence is proven or owned surviving work is safely settled. This applies even to fresh, lost or empty storage when the core reports `recoveryRequired == false`. After unclean host termination, keep execution admission recovery-blocked until previous managed process groups have been reconciled/terminated or verified absent. An ordinary child may survive its parent without deliberately detaching; marking its run interrupted does not free the active slot. Process cleanup must verify ownership and process lifetime/boot identity, not kill a raw reused PID. Proposed launch sequence, so that no user command runs unrecorded: journal the intent (invocation ID and command) before spawning; spawn through a wrapper that records its process ID, group ID, and start time under the invocation ID before exec'ing the command; and tag children with an environment marker carrying the invocation ID. Recovery scans same-user processes for that marker plus start time, because an orphan is reparented and its parent link is gone (platform knowledge; qualify on signed builds). A changed boot session proves absence. If safe reconciliation is impossible, expose unresolved recovery and refuse new execution until absence is established through a reliable local recovery procedure; a mere acknowledgement is not proof that the old process ended. The named reliable procedure is restarting the Mac, and the recovery UI says so. A fresh storage epoch prevents request replay but does not itself settle surviving processes.

A command's observed exit status after host restart does not establish that the entire agent run completed. The core's `confirmRecoveredProcessesAbsent()` asserts absence when called, settles the interrupted run as `interruptedUnknown`, and clears the recovery guard. A later supervisor must preserve separately observed tool-level evidence without promoting it to run completion or automatically resuming recovered commands or agent loops.

Connection state is separate from execution state. Preserve unsent drafts offline, with no hidden delivery queue. If admission is uncertain, resolve the original request against the host before offering a normal resend. Missing/reinstalled hosts remain unavailable, even if a replacement has the same name/IP.

## Cache, files, and resource resolution

Keep a non-synced phone cache keyed by host identity and session ID. It stores host-confirmed list entries, committed transcripts, and explicitly fetched artifacts for offline viewing. It never contains a runnable agent history or authority to submit work. Reconnect reconciles cursor/snapshot state rather than creating local turns.

Exclude this cache from `sync_dirty_records`, normal chat backups/restores, legacy remote-session lists, fork actions, and local execution/usage accounting. Initially exclude it from global local-chat search; offline host chat lists/history remain readable with a stale/offline label. Display host-reported remote usage separately so it is not double-counted. Clearing a cache does not delete host data; host deletion eventually removes corresponding cached content.

Resolve links, attachments, offloaded output, and file actions in the session's host namespace. A remote `minis://` reference must never fall through to phone-local resolution. Use host/session-scoped resource descriptors and explicit authenticated fetches; the builder chooses the URI encoding. Legacy unscoped links are resolved only through their associated host session or shown unavailable. Disable local mention indexing in remote chats.

Structured file reads/writes operate within Mac-selected workspace roots, including symlink/path-traversal enforcement. Present macOS paths. Generated files remain on Mac; downloading/uploading is explicit, with bounded sizes and no implicit overwriting of an existing file. File-service descriptors identify the resource and host/session and are validated server-side on every access. These roots constrain structured file tools, not arbitrary shell commands.

## Approval policy and tool concurrency

Default: each shell invocation and mutating file operation requires approval of its immutable command/change, working directory, effective timeout and delay, host, session/run, and invocation ID. Structured reads within approved workspace roots need no per-read prompt. An approval is single-use with expiry; editing the action or deliberately rerunning requires a new decision.

Proposed optional mode: explicitly authorize one run to execute this declared tool set without further per-action prompts until that run ends, the grant expires, Stop occurs, or authorization is revoked. Do not enable it automatically or persist it to later runs. Its consent must state that ordinary shell commands have the Mac user's permissions, may operate beyond the working folder, and can compromise user-owned host state, including this app's own files, in ways that persist after the run. This is a broader run grant, not a claim of path-enforced shell safety. The phone requires a biometric or passcode check immediately before sending the grant; if the check fails or the device has no passcode, the grant is not offered and per-action approval continues. This check is local to the phone: it guards against casual use of an unlocked device, and the host does not verify it cryptographically. If the user does not accept this mode, per-action approval remains sufficient for v1, with more pauses.

Grant expiry prevents new effectful invocations without a decision: an already admitted command may finish under its own timeout, and the next effectful action returns to per-action approval. Stop, explicit grant revocation, or controller revocation instead cancels the active managed run. Pending per-action approval expiry means that particular action was never admitted; it does not undo previously completed effects.

A pending approval or question produces host `waiting for user` state and an optional attention hint. Disconnect does not approve or deny it. Reopening obtains current state.

On approval expiry, record an explicit timeout indicating nothing was applied/approved, wait for any running reads to settle, record terminal results for the calls that were never admitted so the history stays valid for the provider, end the run, and free the active slot. Serialization below means no admitted effectful command is running at this point. Do not call the model to find another route around approval. There is no paused-run state and no resume operation: the user continues with an ordinary new turn, and any repeated action needs a fresh approval.

A `user_ask` timeout keeps the shared iOS behavior: the model receives a timeout result stating that nothing was applied or approved, plus any unconfirmed suggestion, and the turn continues. Any effectful action it then proposes still needs its own approval. Unlike iOS, where a question can wait indefinitely, Mac sessions always use a bounded timeout because a waiting run holds the active slot. The host enforces its own maximum, proposed at 30 minutes, independent of phone settings, and clamps a phone setting of "wait indefinitely" to it. A `user_ask` answer never substitutes for execution authorization.

Denial stops that run after managed work is settled. Pending effectful calls are cancelled; no provider continuation routes around the denied action. Preserve terminal tool results in original tool-use order. Continuing afterwards is an ordinary new user turn, and a repeated action needs a fresh decision. This remote policy is adapter-specific; existing iOS local semantics are not silently changed.

For the first Mac adapter, fully serialize effectful tools in original tool-use order even when the shared loop dispatches concurrently: ask for or admit the next one only after the previous one has settled, so an approval is never pending while an admitted effectful command runs. Independent reads may run concurrently; all results retain model-required order. Denial and approval expiry therefore never interrupt an admitted effectful command. They cancel calls not yet admitted, wait for running reads to settle, and record already-completed effects truthfully. Only Stop and revocation terminate a running command. Run grants remove prompts but retain this ordering and supervision.

## Process lifecycle, cancellation, and platform access

Run native commands without root or automatic privilege escalation. A working directory is not a shell sandbox. Commands can access other user-accessible files, invoke installed programs, and affect user-owned host state. Dedicated GUI tools are absent, but a shell command is not guaranteed unable to invoke an automation utility; OS permissions govern it.

Use a supervised process group, explicit child ownership, noninteractive stdin from `/dev/null`, and a minimal documented environment without inherited model credentials, application keys, or control sockets. Do not assume `Foundation.Process` automatically supplies the required group semantics. Proposed initial limits: 900 seconds as both the default and the cap on command wall time, with a model-requested `timeout` above it clamped and the limit stated in the result; `delay` capped at 60 seconds and cancelled by Stop, since it holds the active slot with no process to supervise; 64 KiB inline combined output, and at most 16 MiB retained output per command; reaching the retained limit terminates the command with an explicit output-limit result. The host-aware tool descriptions state these limits instead of the current invitation to request larger timeouts. Review these limits during planning, not after unbounded execution exists.

On Stop, the phone says `stop requested` until host confirmation. The host blocks new effects, invalidates grants/approvals, cancels provider streams/retries, and terminates managed processes: graceful termination, then force after five seconds. Settle/join managed work, persist terminal/interrupted state, and emit its event. Bound the join after force termination: an escaped descendant can hold the output pipe open indefinitely, so after a bounded wait close the read ends, mark the output truncated, record that descendants may remain, and settle. The retained-output limit applies to this drain. Stop has no queued prompt to restart in this v1; preserve existing local iOS queue behavior.

Completed changes are not undone. Detached daemons and work handed to external services cannot be claimed stopped merely because the managed group ended; persistent background jobs are unsupported. A crash/forced exit may leave unknown effects: report them and do not auto-rerun.

In the transaction that marks a run interrupted, the host writes a terminal result for each unsettled tool call: "outcome unknown, the command may have run to completion; verify before repeating" for any call with a durable starting record, and "not started" only for calls without one. The shared loop otherwise fills missing results with a generic "interrupted by an unexpected error" ([`AIChatViewModel+AgentLoop.swift`](../../../src/ios/Agent/Chat/AIChatViewModel+AgentLoop.swift)), which would tell the model that a possibly successful command failed and invite a repeat on the next turn. Make that placeholder a seam in the extraction, so it cannot reach the model in a Mac session.

The proposed ordinary-user executor is a directly distributed, appropriately signed native Mac build with App Sandbox disabled, not a Mac App Store target. Sandboxed process children inherit restrictions, so strict sandboxing is a separate runtime choice. Keep OS privacy restrictions: do not automatically request Full Disk Access or Accessibility. Workspace/provider setup should check required file access locally before travel. Later TCC/UI authorization failures or timeouts must become a visible blocked/error state, never an invisible indefinite wait or privacy bypass; exact behavior needs signed-device qualification.

Hold an appropriate activity/idle-sleep assertion while an active run or pending user decision needs hosting, then release it on completion/expiry/Stop. Do not hold the machine awake merely because hosting is enabled. User-forced sleep, power loss, and lid/display configurations can still affect availability; no wake guarantee is made. On return, report actual interrupted/unknown state rather than resuming effects automatically.

Disable hosting/Quit first rejects new work and cancels/settles its managed run before normal exit. Local Mac controls remain available. Abrupt termination is recovered as interrupted/unknown. Device lock does not by itself cancel an authorized run; later Keychain/TCC failures surface explicitly.

## Delivery sequence and evidence gates

These are design gates for the later plan, not authorization to execute now:

1. **Signed transport slice:** minimal Mac service and a standalone iOS test screen with synthetic events over external Tailscale/native TLS. The test screen is throwaway; the production remote backend depends on the gate 2 seams. The stub issues scripted tool actions, with no model, and runs real commands under the native process supervisor. Prove one-time enrollment, host pinning, durable request admission, per-action approval and its expiry, reconnect, Stop settling real process groups, and recovery after killing the host mid-command, including the spawn/journal failure window and refusal of new execution until surviving children are reconciled. This requires a deterministic fault-injection hook for the spawn/journal window, absent from release builds. Use a real iPhone on cellular and the awake Mac before changing the production agent loop. A simulator or unsigned harness is not acceptance.
   **1b. Attention notifications:** add the optional CloudKit path separately, so that its entitlements, schema, and push setup cannot block gate 1 or later gates. Establish which subscription type can deliver the visible generic alert to a locked phone; this is not yet proven. If none can do so dependably, ship the “background alerts unavailable” state rather than presenting silent push as an alert.
2. **Behavior-preserving seams:** characterize the chosen iOS path before each extraction; keep local provider/history/retry/compaction/tool/cancellation behavior. Specify the capability and signing/dependency inventory. Existing device-only iSH dependencies limit simulator builds; use appropriate source/unit/physical evidence without claiming simulator coverage that does not exist.
3. **First native agent slice:** one supported API-key provider, text chats, same-provider request retry, native shell/files, user questions, approvals, durable host storage, separate phone cache, and scoped resources. Reaching the context limit stops the chat with an explicit error. Qualify a disposable workspace under actual signed Mac permissions.
4. **Shared compaction:** extract compaction behind the shared interfaces, characterizing the iOS path first, and enable it for Mac sessions. Long Mac chats continue past the context limit using the same implementation as iOS.
5. **Combined qualification:** exercise physical away-from-home use, phone suspension, host sleep/restart, request/notification duplication, denied/expired approvals, signed app dependencies, and existing local iSH networking (`apk`, `pip`, `git`) with the Tailscale VPN on, since the phone now keeps it on and [`NetworkMonitor.swift`](../../../src/ios/Shared/NetworkMonitor.swift) already records Tailscale DNS breaking those tools. Only then evaluate broader provider/tool coverage or automatic discovery as separately scoped work.

If retained native libraries contain Go, verify actual signed launch and avoid linking multiple Go runtimes into one process. External Tailscale introduces no new in-process Go runtime; there is no reason to add one merely for transport. Existing rclone/iSH and signing issues still require an inventory rather than being assumed solved by this network simplification.

Required adversarial/recovery evidence: unapproved peer and wrong host key refused; pairing secret expiry/replay/impersonation refused, and a racing enroller exposed by a mismatched code; revocation prevents further admissions; repeated request IDs do not rerun effects; a lost acknowledgment leads to a status lookup and never an automatic resend, except Stop; Reset Host requires new enrollment; a Time Machine restore yields a fresh epoch and a move to a new Mac yields a new host; a phone cursor ahead of the host's head produces a reset rather than an empty change list; a busy rejection remains rejected on retry after idle; deleted-session and pre-reset-epoch retries remain rejected; crash between effect and result remains unknown, both in the journal and in what the model is told on the next turn; surviving managed children block new execution until safely reconciled, including the spawn/journal failure window; replay/cache cannot activate local execution; wrong-host links never open local files; expired/denied concurrent actions cannot route around authorization; run-grant expiry admits no new effects and differs from Stop/revocation; an expired approval ends the run, frees the active slot, and leaves history the provider accepts on the next turn; a timed-out `user_ask` approves nothing; phone locked at first tool call gets best-effort attention and otherwise waits; missing iCloud/notifications do not break foreground use; tailnet policy/network failure has no routing fallback; TCC failures, command/output limits, idle sleep, and managed process termination report truthful states, and Stop settles even when an escaped descendant holds the output pipe; application logs respect the redaction contract.

## Remaining planning choices

Choose concrete module/API boundaries, framing/version compatibility, TLS/platform key integration, pairing encoding/limits, the existing API-key adapter, transaction schema/version/migrations, cursor retention/coalescing, deployment targets, and signed-build configuration. Qualify synchronous SQLite work on a dedicated executor for host responsiveness; no dedicated executor or performance qualification is implemented by the initial package. These choices must satisfy the contracts above; do not silently add OAuth, queues, cross-device tools, cloud discovery, or a shell-isolation promise.

User review should particularly consider the proposed run-grant option, ordinary-user shell authority, one-controller/one-active-run limit, initial API-key-only capability surface, optional background alerts, and no PTY. The user has now authorized the two review corrections and starting implementation. Begin with a bounded implementation and verification plan. The first increment implements durable admission and reconnect fencing as portable foundation code; it does not qualify the signed/native transport gate or authorize extraction into the production agent loop. No commits, provisioning, live Tailscale/account changes, or publication are implied.
